# Ultimate Remote protocol 1

Protocol 1 is a closed JSON protocol between the central backend and one
`UltimateRemoteAgent` installation. It is intentionally not a general remote-control
protocol.

## Transport and authentication

- The Agent makes an outbound WebSocket connection to `/remote/v1/agent`.
- Every message is UTF-8 JSON text, at most 64 KiB. Binary messages, duplicate JSON
  keys, missing fields, and unknown fields are rejected.
- Every envelope contains `"protocol": 1`.
- The HTTP upgrade carries `Authorization: Bearer <device credential>`. Credentials
  never appear in a URL or JSON message.
- A credential is generated by the server, unique per installation, random at 256
  bits, revocable, and returned only once. SQLite stores its SHA-256 digest, not the
  bearer value.
- `ws://` is permitted only on a literal loopback address. A second PC must use a
  trusted `wss://` endpoint, either through direct TLS or a TLS reverse proxy that
  preserves the `Authorization` and WebSocket upgrade headers.
- The credential identifies the device. No message may override that identity with a
  caller-supplied device ID.

R2 obtains this credential out of band through the isolated temporary development
pairing flow in [`remote-pairing-v1.md`](remote-pairing-v1.md). Pairing is not a
protocol-1 message or operation. A pairing ticket is invalid on this WebSocket, and a
device bearer is invalid on the pairing endpoint. Replacing development pairing with
OAuth later does not change any HELLO, WELCOME, heartbeat, command, or update schema.

Closed-schema fields are exact: snapshot keys are always present (the current strategy
may be JSON `null`), while result/error fields that do not apply to a command update
must be omitted rather than emitted as `null`. WebSocket fragmentation is handled by
the WebSocket library; validation applies after a complete text message is assembled.

The first Agent message must arrive within ten seconds and must be `HELLO`. The server
sends `WELCOME` before making that connection eligible for command dispatch. A normal
heartbeat interval is 30 seconds; the development server treats 90 seconds of silence
as offline.

## Operation allowlist

Protocol 1 implements exactly:

- `GET_STATUS`
- `LIST_STRATEGIES`
- `START_STRATEGY`
- `STOP_SAFE`
- `SWITCH_STRATEGY`

The names `RESTART_MACRO`, `GET_AUTO_EQUIP`, `SET_AUTO_EQUIP`, and `GET_DIAGNOSTICS`
are reserved for a future protocol revision and are rejected in protocol 1.

There is no `EXEC`, `SHELL`, `CMD`, `POWERSHELL`, arbitrary executable path, download,
file browser, or remote desktop operation. Adding an operation requires a protocol
change and an explicit implementation on both sides.

## Strategy identifiers

The wire carries an opaque `strategy_id`, never a filename or path. It is 8-64 ASCII
letters, digits, underscores, or hyphens and must begin with a letter or digit. The
Agent returns display text separately in `LIST_STRATEGIES`; Discord displays the name
but submits the corresponding ID.

The Windows Agent milestone must generate a deterministic ID as follows:

1. Enumerate only an approved local root (initially the top level of
   `Resources\Strats`) and require `.strat`.
2. Form the catalog key from the fixed initial root label `builtin`, a NUL separator,
   and `filename.Normalize(FormC).ToUpperInvariant()`.
3. SHA-256 hash the UTF-8 catalog key, Base64url-encode all 32 digest bytes without
   padding, and prefix `s_`.
4. Reject duplicate normalized keys or IDs.

Golden vector: `builtin`, NUL, and `EXAMPLE.STRAT` hashes to
`s_kjr-1a5HJUSQFEg2FqPYT2mO4PCYETBQQIUyI-rvxC8`.

Renaming a file changes its ID. The Agent maintains the ID-to-canonical-local-path map
and resolves only an ID returned by its own current catalog. Before writing the legacy
AHK mailbox it must independently reject rooted, UNC, device, traversal, wrong-extension,
outside-root, and reparse-point escapes. An absolute local path may exist only on the
Agent-to-AHK side; it never crosses this protocol.

If the macro is running a strategy outside the approved Remote catalog,
`current_strategy_id` is `null`. The Agent must not upload the local path or fabricate
an ID.

## Handshake

Agent to server:

```json
{
  "protocol": 1,
  "type": "HELLO",
  "agent_version": "0.1.0",
  "supported_operations": [
    "GET_STATUS",
    "LIST_STRATEGIES",
    "START_STRATEGY",
    "STOP_SAFE",
    "SWITCH_STRATEGY"
  ],
  "snapshot": {
    "macro_state": "idle",
    "roblox_running": false,
    "current_strategy_id": null
  }
}
```

The full list in the generic example above is the eventual protocol-1 capability set.
The R3 Agent advertises only `GET_STATUS` and `LIST_STRATEGIES`; central therefore
refuses to dispatch the three mutating operations to it. R3 still parses their closed
wire shapes so it can return a fixed `OPERATION_UNSUPPORTED` failure if a
nonconforming server sends one, but it never accepts, journals, or executes them
locally.

Server to Agent:

```json
{
  "protocol": 1,
  "type": "WELCOME",
  "heartbeat_interval_seconds": 30,
  "server_time": "2026-08-15T18:00:00.000Z",
  "reconcile_commands": []
}
```

`reconcile_commands` contains IDs and operation names only. It is not a replay request
and contains no arguments. A mutation-capable Agent must compare each entry with its
durable local command journal, the exact AHK mailbox ID, and the exact AHK result ID,
then report the known state. The read-only R3 Agent has no mutation journal: it records
only that reconciliation metadata was received and sends no update for it. An Agent
must never execute an operation merely because it appears in this list.

## Heartbeat and snapshot

```json
{
  "protocol": 1,
  "type": "HEARTBEAT",
  "snapshot": {
    "macro_state": "running",
    "roblox_running": true,
    "current_strategy_id": "s_bJhItQpW5V4dG3ZxTUK5nYk4TWVxXqf0xH2g-dummy"
  }
}
```

`macro_state` is one of `not_running`, `idle`, `running`, or `unknown`. `last_seen`,
online/offline, Agent version, and protocol version are server-owned state. Agent
timestamps are not authoritative. `running` means the Agent has positively identified
the exact Remote-capable macro process and an active strategy lifecycle; the early
`state.ini` `Running=1` value alone is insufficient.

## Commands

The three operations without an argument use an empty object. START and SWITCH contain
only a strategy ID.

```json
{
  "protocol": 1,
  "type": "COMMAND",
  "command_id": "11111111-1111-4111-8111-111111111111",
  "operation": "START_STRATEGY",
  "issued_at": "2026-08-15T18:00:00.000Z",
  "expires_at": "2026-08-15T18:00:30.000Z",
  "arguments": {
    "strategy_id": "s_bJhItQpW5V4dG3ZxTUK5nYk4TWVxXqf0xH2g-dummy"
  }
}
```

`expires_at` is the delivery-acceptance deadline, not an execution deadline. STOP and
SWITCH may remain executing throughout the current match and until the validated safe
boundary. The Agent must not newly accept an expired command.

Wire timestamps use canonical UTC `yyyy-MM-dd'T'HH:mm:ss.fff'Z'`. The Agent parses them
as UTC `DateTimeOffset` values, but central enforcement is authoritative if clocks skew.

## Command states

The durable central lifecycle is:

```text
queued -> accepted -> executing -> completed
   \--------\----------\---------> failed
              \------ connection loss ------> reconciling
```

- `queued`: persisted centrally and sent, but not acknowledged by the Agent.
- `accepted`: the Agent validated the operation. R3 holds read-only command state only
  in memory; before acknowledging a mutating operation, a future Agent must durably
  journal its command ID.
- `executing`: read-only sampling has begun, or a fixed local mutation has begun or is
  waiting at the AHK safe boundary.
- `completed`: the operation-specific postcondition below is true.
- `failed`: normally the Agent has a definite sanitized failure result. Administrative
  device revocation also terminalizes unresolved work with
  `DEVICE_REVOKED_OUTCOME_UNKNOWN`; that code explicitly does not claim the local action
  was prevented, because a revoked credential can no longer reconnect to reconcile it.
- `reconciling`: central lost the connection or delivery deadline without proof of the
  local outcome. This is a server-owned, fail-closed state. It blocks another mutating
  command, is advertised in the next WELCOME, and is never automatically replayed.

Only START/STOP/SWITCH can have an ambiguous external side effect and therefore enter
`reconciling`. An interrupted GET_STATUS or LIST_STRATEGIES safely becomes `failed`.

The Agent reports accepted/executing without a result:

```json
{
  "protocol": 1,
  "type": "COMMAND_UPDATE",
  "command_id": "11111111-1111-4111-8111-111111111111",
  "status": "accepted"
}
```

A completed status/list/action carries exactly one typed result. A failed status carries
only a stable uppercase error code and a short sanitized message.

Completed gameplay-changing actions carry both a snapshot and fixed bridge evidence:

```json
{
  "protocol": 1,
  "type": "COMMAND_UPDATE",
  "command_id": "11111111-1111-4111-8111-111111111111",
  "status": "completed",
  "snapshot": {
    "macro_state": "running",
    "roblox_running": true,
    "current_strategy_id": "s_kjr-1a5HJUSQFEg2FqPYT2mO4PCYETBQQIUyI-rvxC8"
  },
  "action_result": "strategy_started"
}
```

```json
{
  "protocol": 1,
  "type": "COMMAND_UPDATE",
  "command_id": "11111111-1111-4111-8111-111111111111",
  "status": "failed",
  "error": {
    "code": "STRATEGY_NOT_FOUND",
    "message": "The selected strategy is no longer installed."
  }
}
```

The Agent contract requires the following completion evidence. Central validates the
reported snapshot/list shape, target ID, Roblox START state, and fixed action-result
code; the R4 Agent must separately correlate the exact local AHK command/result ID
before it reports completion:

- `GET_STATUS`: any valid snapshot.
- `LIST_STRATEGIES`: a path-free list of unique `{strategy_id, name}` objects.
- `START_STRATEGY`: `action_result=strategy_started`, `macro_state=running`, Roblox
  running, and the requested strategy ID. The existing AHK `start_accepted` marker
  means only executing; it occurs before Roblox/join and is not completion.
- `STOP_SAFE`: `action_result=stopped_safe` and `macro_state` is `idle` or
  `not_running`; the Agent reports this only after the matching AHK result.
- `SWITCH_STRATEGY`: `action_result=switched_safe` and `macro_state=running` with the
  requested strategy ID. This means the switch was applied at the safe boundary, not
  that a new match has finished joining.

The server correlates every update to both the authenticated device and command ID,
enforces monotonic transitions, accepts only identical terminal replays, and never
resends a command after reconnect.
